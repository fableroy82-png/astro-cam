============================================================
4. ROTATION PHYSIQUE DE LA CAMÉRA
============================================================

La caméra est actuellement montée en diagonale.

Exemples de rotation WCS observée :
- environ -37° sur la dernière capture.
- auparavant autour de -49° / -54° selon les essais.

Conséquence :
- les mouvements physiques haut/bas et gauche/droite apparaissent en diagonale à l'écran ;
- les flèches bleues/vertes sont donc pénibles à interpréter ;
- même si les calculs sont corrects, l'ergonomie reste mauvaise.

PLAN POUR DEMAIN :
1. Tourner physiquement la caméra / le tube.
2. Essayer d'obtenir :
   - MONTER = visuellement vers le haut de l'écran ;
   - DESCENDRE = vers le bas ;
   - GAUCHE = vers la gauche ;
   - DROITE = vers la droite.
3. Faire un montage permettant de viser dehors si nécessaire.
4. Une fois la caméra physiquement alignée, refaire une calibration propre.

IMPORTANT :
>>> Ne pas continuer à multiplier les corrections logicielles d'axes AVANT cette remise à l'équerre physique.

============================================================
5. CALIBRATION À REFAIRE APRÈS ALIGNEMENT CAMÉRA
============================================================

Quand la caméra sera physiquement remise droite :

Faire un test avec UNE étoile reconnaissable.

Test ALT :
- bouger physiquement vers le haut ;
- noter précisément dans quel sens l'étoile se déplace à l'écran ;
- bouger vers le bas ;
- confirmer le sens opposé.

Test AZ :
- tourner physiquement à droite ;
- noter le déplacement écran ;
- tourner physiquement à gauche ;
- confirmer le sens opposé.

Ensuite seulement :
- fixer les quatre directions logiciellement ;
- vérifier les signes AZ/ALT ;
- vérifier qu'un mouvement demandé fait DIMINUER la distance à la cible au solve suivant.

Critère de validation :
Distance cible :
5.0° -> 3.5° -> 2.0° -> 0.8° -> cible dans le champ.

6. INDICATIONS VISUELLES À REFAIRE
============================================================

C'est le gros chantier à faire demain.

Objectif :
En regardant l'écran, l'utilisateur doit comprendre IMMÉDIATEMENT quoi faire.

À conserver :
- flèche JAUNE = direction globale vers la cible ;
- cible ROUGE + nom de l'objet (ex. M11) ;

À améliorer :

- texte court ;
- éviter les phrases techniques trop longues ;
- éviter les informations redondantes ;
- éviter les blocs illisibles en bas à gauche.

Exemple de HUD recherché :

TOURNE À DROITE 3.9°   |   MONTE 1.1°

Ou une présentation graphique encore plus claire.

Le texte doit être orienté ACTION :
- TOURNE À DROITE
- TOURNE À GAUCHE
- MONTE
- DESCENDS

Pas besoin d'obliger l'utilisateur à interpréter :
- RA/DEC ;
- Est/Ouest céleste ;
- rotation caméra ;
- vecteurs mathématiques.

Le calcul peut rester complexe en interne, mais l'interface doit être simple.

9. PROBLÈME CAMÉRA / RECONNEXION
============================================================

Pendant les nombreux essais :
- arrêt du script ;
- copie d'une nouvelle version ;
- redémarrage ;
- répétition plusieurs fois ;

la SC715C a fini par décrocher.

Le programme a essayé de se reconnecter automatiquement mais n'a pas réussi.

Action qui a fonctionné immédiatement :
- débrancher physiquement l'USB caméra ;
- rebrancher ;
- pendant que le programme essayait encore de récupérer la caméra ;
- la caméra est repartie immédiatement.

Conclusion provisoire :
- probablement état USB / SDK / caméra bloqué après trop de cycles rapides ;
- pas forcément un bug prioritaire du programme ;
- la récupération logicielle V20+ ne suffit pas toujours quand l'USB/caméra est réellement coincé.

À examiner plus tard :
- délai d'arrêt caméra plus long ;
- délai après DISCONNECT INDI ;
- délai avant arrêt d'indiserver ;
- délai au démarrage avant tentative de reconnexion ;
- éventuellement plusieurs tentatives de reconnexion espacées ;
- éventuellement détecter disparition/réapparition USB.

Ne pas casser le fonctionnement actuel pour ça.
Le problème apparaît surtout parce qu'on enchaîne énormément de redémarrages pendant le développement.
